# 热更新（应用内自动更新）调研

> 调研日期：2026-07-27
> 范围：本项目（Tauri 2 + NSIS 安装包 + 便携版 exe，GitHub Releases 分发）如何让用户不必手动下载安装包即可升级。依据为 Tauri 官方文档、`tauri-plugin-updater` 源码（已逐段核对 Windows 安装路径）与社区实践；不依赖未验证的博客说法。

## 术语澄清

「热更新」在桌面应用语境下有三种含义，结论不同：

| 含义 | 本项目可行性 |
| --- | --- |
| A. 应用内自动更新：应用自查新版 → 下载 → 静默安装 → 自动重启 | **可行**，官方 `tauri-plugin-updater` 直接支持，是本文主体 |
| B. 资源级热替换（CodePush 式）：不重装、不重启，只换前端资源 | Tauri **官方不支持**，为开放需求（[#13343](https://github.com/tauri-apps/tauri/issues/13343) 已并入 [#11696](https://github.com/tauri-apps/tauri/issues/11696)）；不建议自行实现，见下 |
| C. 开发期热重载 | 与分发无关；当前 `tauri dev` 改前端需手动刷新，如有需要可另配 devUrl + 静态服务器，本文不展开 |

## 结论先行

1. **推荐落地 A：官方 updater 插件，NSIS 安装版可全自动升级。**流程为启动后台检查 → 用户确认 → 下载并校验 minisign 签名 → 应用自动退出 → NSIS 静默安装 → 安装器自动拉起新版本（源码确认 `restart_after_install` 默认开启，且透传原命令行参数）。当前 NSIS 为 per-user 安装，升级不弹 UAC。
2. **便携版 exe 无法被 updater 升级。**插件源码中 Windows 更新类型只有 NSIS 与 MSI；下载到裸 exe 会被当作 NSIS 安装器执行，结果错误。便携版应走「检查到新版 → 提示 + 打开发布页」的半自动路径，检查逻辑可与安装版共用。
3. **B（免重启换前端资源）收益低、代价高，不建议。**本项目校准逻辑一半在 Rust（NTP、reqwest 请求、托盘），纯前端可热换的改动很少；自行实现需要把资源移出二进制、自建下载与校验通道，绕开刚加固的 CSP 与官方签名体系，等于自造一条无签名的代码注入通道。等官方 #11696 落地再评估。
4. **主要风险是国内网络，不是技术实现。**目标用户在大陆，GitHub Releases 直连下载经常不可用。updater 支持多 endpoint 依序尝试；minisign 签名使第三方镜像最多导致「更新失败」，不可能导致「被投毒」（篡改产物无法通过公钥校验）。建议第一阶段 GitHub 直连 + 失败时清晰提示手动下载，第二阶段按用户反馈再加镜像。
5. **一次性成本是签名密钥与发布流程改造。**需要生成 minisign 密钥对（私钥绝不入库，丢失则存量用户永远收不到可校验的更新，只能手动重装）、`build.ps1` 增加生成 `latest.json` 的步骤、每次 release 多上传 `latest.json` 与 `.sig`。编码量集中在 `lib.rs` 托盘与检查逻辑，估计半天到一天（含真实升级链路验证）。

## 机制细节（已核实）

### 构建与签名

- `tauri signer generate` 生成密钥对；构建时通过环境变量 `TAURI_SIGNING_PRIVATE_KEY`（内容或路径）与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 提供私钥，公钥写进 `tauri.conf.json`。
- `bundle.createUpdaterArtifacts: true` 后，NSIS 安装包旁会生成 `*-setup.exe.sig`。签名针对文件内容，`build.ps1` 现有的改名复制不影响校验，`latest.json` 的 `url` 指向改名后的资产即可。

### 更新清单

约定俗成的做法是把 `latest.json` 作为 release 资产上传，endpoint 用 GitHub 的固定转发地址（也支持动态服务端，返回 204 表示无更新；本项目无后端，用静态清单即可）：

```
https://github.com/zionyang/floating-clock/releases/latest/download/latest.json
```

```json
{
  "version": "0.1.4",
  "notes": "更新说明",
  "pub_date": "2026-07-27T00:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "url": "https://github.com/zionyang/floating-clock/releases/download/v0.1.4/FloatingClock-0.1.4-tauri-win-x64-setup.exe",
      "signature": "<对应 .sig 文件内容>"
    }
  }
}
```

版本比较按 semver，仅当远端大于当前版本才提示更新。`latest.json` 可由 `build.ps1` 从版本号、资产 URL 与 `.sig` 内容自动生成，避免手工拼写。

### Windows 安装行为（以插件源码为准）

[`updater.rs`](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs) 的 `install_inner`：

1. 触发 `on_before_exit` 钩子（可用于保存状态）；
2. `ShellExecuteW` 启动下载好的 NSIS 安装器，参数为安装模式（默认 passive，带进度条；可选 quiet 全静默）加 `/UPDATE`；
3. 当前进程立即 `std::process::exit(0)`——**Windows 上 `download_and_install` 之后的代码不会执行**，无需也来不及调用 `relaunch()`；
4. `restart_after_install` 默认 `true`：安装器附带重启参数与 `/ARGS`，装完自动拉起新版本并透传原始命令行参数。单实例插件无冲突，旧实例在安装前已退出。

### 与现有配置的关系

- **CSP 无需改动**：更新检查与下载走 Rust 侧 reqwest，不经过 WebView。
- **capabilities 无需改动**：推荐纯 Rust 侧使用 `UpdaterExt`（托盘与后台逻辑本就在 `lib.rs`），不注册 JS 权限；与 `removeUnusedCommands: true` 兼容，未授权的 IPC 命令会被裁剪。若未来想在前端页面里做更新 UI，再加 `updater:default` 权限即可。
- **WebView2 不受影响**：升级不重装运行时。

## 本项目落地方案（建议）

| 项 | 改动 |
| --- | --- |
| `Cargo.toml` | 新增 `tauri-plugin-updater = "2"` |
| `tauri.conf.json` | `bundle.createUpdaterArtifacts: true`；`plugins.updater` 写 `pubkey` 与 `endpoints` |
| `lib.rs` | 注册插件；启动后延迟数秒静默检查 + 每日一次；托盘新增「检查更新」与「发现新版本 x.y.z」入口，用户点击后才 `download_and_install` |
| `build.ps1` | 校验签名环境变量存在；复制 `.sig` 到 `dist/`；生成 `dist/latest.json` |
| `docs/打包流程.md` | 发布步骤补充上传 `latest.json`；新增密钥保管与丢失后果说明 |
| 便携版 | 共用检查逻辑，仅提示新版本并打开发布页；安装版/便携版的判别（如按注册表卸载项或安装路径）在实现时定 |

交互约束（针对抢购场景）：检查静默进行，结果只体现在托盘菜单/提示，**绝不自动弹窗、绝不自动安装**——避免在整点抢购前被更新流程打断；安装动作永远由用户主动触发。

验证路径：先用 GitHub pre-release 走一遍真实 `0.1.x → 0.1.y` 升级（安装旧版 → 发布新版 → 托盘检查 → 静默安装 → 自动重启核对版本号）；本地调试可临时开 `dangerousInsecureTransportProtocol` 指向本机静态服务器，验证后移除。

### 国内网络的分阶段策略

1. **第一阶段（先做）**：endpoint 仅 GitHub。检查失败或下载失败时，界面/托盘明确提示「无法连接更新服务器」，并提供打开发布页的入口，不做静默吞错。
2. **第二阶段（按反馈）**：追加镜像 endpoint（`gh-proxy` 类前缀或自建 Cloudflare Worker）。注意镜像必须连 `latest.json` 里的 `url` 一起改写/代理，否则清单能拿到、安装包仍从 GitHub 直连下载导致失败。签名机制保证镜像不可信也只影响可用性，不影响完整性。

## 风险与对策

| 风险 | 等级 | 对策 |
| --- | --- | --- |
| 私钥丢失/泄露 | 高 | 私钥离线备份，不入库不进日志；泄露则换钥并要求用户手动装一次新版 |
| GitHub 大陆不可达 | 高 | 分阶段镜像策略（见上）；失败时引导手动下载 |
| 便携版用户无自动更新 | 中 | 提示 + 打开发布页；文档说明差异 |
| 更新流程打扰抢购时刻 | 中 | 静默检查、被动提示、仅手动安装 |
| 发布漏传 `latest.json`/`.sig` | 低 | `build.ps1` 生成并校验齐全，发布核对清单加入打包流程文档 |
