# 时间源校准：社区与 GitHub 开源做法调研

> 调研日期：2026-07-23
> 范围：京东、美团、美团闪购、淘宝闪购等当前不能保证毫秒精度的时间源；重点阅读 GitHub 源码、README、Issue 与实际接口表现，不把非公开接口、逆向签名或过期脚本当成稳定依赖。

## 结论先行

1. **没有找到可证实、当前公开且无需账号/签名、可为美团或美团闪购提供毫秒级服务端时间的接口。**社区中的美团抢购脚本通常靠提前预热、最后一秒轮询和重试，不是公共毫秒时钟方案；其中能找到的实现还明确提示高频请求会触发 `403`，且签名算法已失效。
2. **京东的开源脚本中确实存在“服务器时间差值 + 本机调度”的做法，但历史 `serverTime` 端点不能直接采纳。**本机在本次调研中请求 `https://a.jd.com/ajax/queryServerData.html` 得到的是 `text/html`，不是旧脚本预期的 JSON。因此它只能作为历史实践证据，不能作为当前项目的默认时间源。
3. **HTTP `Date` 不是毫秒时间戳。**它最多提供秒级服务器日期；通过两次请求夹逼秒边界可以给出区间估计，但误差下限由两次串行请求的时延、排队和边界采样方式决定。它可以显示估计误差，不能无条件标为“毫秒级”。
4. 对本项目而言，最可靠的路线不是复制抢购脚本的高频轮询，而是：**直接毫秒字段优先；NTP 多源估计偏移；HTTP `Date` 仅作为带误差的秒级后备；校准完成后以本机单调时钟运行倒计时。**

## 本项目当前实测为何失败

当前相位策略要求 `uncertaintyMs <= 100`，而不确定性是跨秒窗口的一半，因此只有跨秒窗口不超过 200 ms 才能成功。相关实现见：

- [`src/time-sources.js`](../src/time-sources.js)：14 次串行探测、每次后等待 80 ms、最大不确定性 100 ms；
- [`src/time-core.js`](../src/time-core.js)：窗口是“前一次请求开始”到“下一次请求结束”；
- [`src-tauri/src/lib.rs`](../src-tauri/src/lib.rs)：相位探测请求会下载完整响应体，单次总超时为 1 秒。

2026-07-23 的同形请求实测结果如下：

| 源 | 最小跨秒窗口 | 对应最小估计误差 | 当前阈值下的结果 |
| --- | ---: | ---: | --- |
| 京东 `api.m.jd.com` | 341 ms | ±171 ms | 拒绝 |
| 淘宝闪购 `www.ele.me` | 347 ms | ±174 ms | 拒绝 |
| 美团闪购 `brandhub.meituan.com` | 472 ms | ±236 ms | 拒绝 |
| 美团 `www.meituan.com` | 686 ms | ±343 ms | 拒绝 |

美团两个端点本轮均返回 `200` 和递增的 `Date`，未出现 `Age` 缓存命中；失败不是 403、缺少 `Date` 或单次超时，而是测得的网络路径不满足 ±100 ms 所需的 200 ms 窗口。

## GitHub 与社区实践

### 1. 京东：先估计一次偏移，再用本机时钟调度

| 来源 | 可复核事实 | 可借鉴之处 | 不能据此得出的结论 |
| --- | --- | --- | --- |
| [wdmic/jd_java README（固定提交）](https://github.com/wdmic/jd_java/blob/8250b90edf60aa05b4ffd78cbf1d02e22d00a9ec/README.md) | README 说明启动时计算本地时间与京东服务器时间的毫秒差，后续按本机时钟执行。 | 将“校准”与“临近目标的业务请求”分离；先收集 offset，再本地调度。 | README 没公开端点、采样方法或误差模型，不能把其“毫秒差值”当作已验证的毫秒精度。 |
| [andyzys/jd_seckill `timer.py`（固定提交）](https://github.com/andyzys/jd_seckill/blob/0e5c53575862bc83ca1702191f10a1c2128ff1b3/timer.py) | 代码使用 `datetime.now()` 和 0.5 秒轮询；主流程把登录、商品和结算准备放在目标前。 | 社区脚本把准备工作、调度与重试放在时间同步之前，避免将所有成功率寄托在一个远端时钟上。 | 这不是远端时间校准，更不能证明 0.5 秒轮询适合毫秒级倒计时。 |
| [woxiqingxian/jd_seckill](https://github.com/woxiqingxian/jd_seckill) | 当前仓库源码仍可见使用 `a.jd.com/ajax/queryServerData.html` 的历史做法：读取 JSON `serverTime` 后估算本地差值。 | 证明 `serverTime` 直取在社区中曾经广泛使用。 | 本次本机实测该 URL 已返回 HTML 而非 JSON；不可把旧代码复制为当前生产策略。 |

**对京东源的结论：**若未来找到并实测可用、明确返回毫秒字段的端点，可新增为“直取毫秒时间”的候选策略，并保存最近实测结果与错误类型；在此之前，当前主页 `Date` 相位法应降级为带误差的后备，而不是承诺 ±100 ms。

### 2. 美团：社区抢购代码侧重预热与轮询，不提供可复用时钟

[shixiangkuangmo/meituan README（固定提交）](https://github.com/shixiangkuangmo/meituan/blob/ba7f9ddd8192d80e049128ac819eafcd6c79cc71/README.md) 写明其操作节奏是“提前 20 秒启动、开始前 1 秒发送请求、间隔 100 ms”，同时提示高频请求会出现 `403`，并声明 app 端签名算法已过期、项目不可用。

这份代码的价值是说明社区实践，而不是提供实现模板：

- 它没有提供公开、稳定、无签名的美团毫秒时钟接口；
- 100 ms 业务请求轮询属于抢购策略，不是时间校准，会触发风控并放大请求量；
- 已失效的逆向签名、Cookie、账号态或购买请求都不应进入 FloatingClock。

**对美团和美团闪购源的结论：**截至本次调研，没有可证实的替代毫秒字段可安全替换官网 `Date`。保留它们只能定位为“HTTP `Date` 秒级时间，显示实测误差”；若用户要求小于约 ±250 至 ±350 ms 的精度，应显示“不满足精度要求”，而不是伪造一个毫秒偏移。

### 3. 淘宝/淘宝闪购：公开时间戳的可用性会变化，不能从历史文章反推当前能力

淘宝主站现有的 `mtop.common.getTimestamp` 与本项目的实测直接毫秒字段是另一类来源；但社区 Issue 已记录类似时间戳接口会发生异常或失效，例如 [Sitoi/dailycheckin #433](https://github.com/Sitoi/dailycheckin/issues/433)。这类讨论支持一个工程结论：即使端点今天返回毫秒字段，也必须有运行时校验和降级状态，不能只因旧教程或旧仓库使用过就永久信任。

对淘宝闪购（当前使用 `www.ele.me` 的 `Date`）而言，本次没有找到可固定到可复核 GitHub 源码、并能验证返回现行 `server_time` 或等价毫秒字段的公开实现。该结论是“未找到可证实方案”，不是“该平台绝无内部接口”。内部、登录态、签名或业务接口不属于本应用可依赖的公共时间源。

## 封闭源客户端的反证：功能存在，不等于公开实现可复用

用户提供的 iPhone 应用 [悬浮时钟-抢购秒杀助手（App Store ID 1546947240）](https://apps.apple.com/cn/app/id1546947240) 是一个重要反例：它证明同类产品确实能向终端用户提供多平台时间源，而不是“市场上没有这种功能”。此前本报告的结论应严格理解为：**本轮没有找到可公开复现、无需账号或签名、并能为本项目直接采用的毫秒接口或开源实现**；它不对封闭源产品的内部能力作否定判断。

### 已能从 App Store 公开页面核实的内容

App Store 的中国区公开元数据（2026-07-23 读取，版本 5.2.4，开发者为 Hangzhou OrangeJuice Technology Co., Ltd.）明确写有：

- “毫秒级悬浮时钟”；
- “多平台时间同步：主流平台全支持”；
- 开发者在公开回复中表示“时间源可以自行选择合适的，也可手动调节”；
- 5.2.3 的公开版本记录提到“时间源优化，用户可以方便地对比设备时间/时间源时间”。

这些材料足以证明该产品有**可选时间源、人工偏移调节和设备/来源时间对比**的产品能力；也与用户实际看到淘宝、天猫、京东、大麦、拼多多、云闪付和美团等源相一致。

| 已公开或用户可直接观察到的能力 | 公开页面没有披露、不能推断的实现细节 |
| --- | --- |
| 多平台时间同步、可选择时间源、手动调节、显示毫秒、比较设备时间与来源时间 | 每个平台的 URL/协议、是否为直接服务端毫秒字段、是否经过自建代理、采样次数、RTT/缓存处理、误差模型、失效后的降级逻辑 |

App Store 的公开文案没有列出上述平台名称，也没有提供 API、网络协议、精度测试或开源代码；因此不能据此推断它使用某个公开美团或云闪付端点，更不能复制其实现。

### Android “悬浮秒表”的识别边界

用户说明华为手机正在使用名为“悬浮秒表”的同类应用，且时间源更多。这是有价值的使用证据，但“悬浮秒表”不是足以唯一定位应用的标识：本轮公开检索未取得可唯一确认的华为应用市场详情页、开发者或包名。故本报告不把任何同名候选的接口归因给该应用。

若需要把它纳入可复核对标，最小识别信息是以下任一项：华为应用市场详情页链接、开发者名称、包名、版本号，或包含“关于/隐私政策”页的截图。即使得到这些信息，研究也应仅分析公开声明和可由用户主动导出的显示结果；不应对第三方商业应用进行抓包、反编译或绕过访问控制。

### 对本项目结论的修正

成熟封闭源客户端至少提示了两件事：

1. “来源列表丰富”可以是可用的产品体验，前提是它同时展示来源选择、设备时间对比和人工调节，而非承诺每个来源都是同等精度的公开毫秒 API。
2. FloatingClock 应把重点从“猜测每个平台的私有端点”移到可验证体验：记录来源、校准时间、偏移、RTT、估计误差和保留时长；不能自动保证时，允许用户在明确风险下人工调节。

这不改变前文对公开接口的安全边界：不引入 Cookie、签名、账号态或高频业务轮询；也不把第三方客户端的宣传语当作本项目的精度证明。

## 推荐的工程策略

### 时间源分级

| 等级 | 例子 | UI 与行为 |
| --- | --- | --- |
| A：直接毫秒字段 | 当前拼多多 `server_time`、淘宝 `data.t` | 最多多次采样，选低 RTT 样本；显示 RTT 与估计误差。 |
| B：NTP | 北京时间 | 同时维护多个经过实测的 NTP 源；验证报文来源时间戳；按 RTT、离群值和成功率选择结果。主源连续超时应切换备源并展示来源。 |
| C：HTTP `Date` | 当前京东、美团、美团闪购、淘宝闪购 | 明确标成“秒级 HTTP 日期估计”；只在估计误差小于用户要求时可用，显示 `±N ms`，不得标为“毫秒级”。 |
| D：本机保留偏移 | 任一源短暂失败后的运行态 | 只在界面说明“保留上次校准，已过期 N 秒”；不得声称仍在实时校时。 |

### 校准与倒计时分离

1. 在目标前较早时间段完成多样本校准，保存 `offset`、RTT、估计误差、成功率和校准时间。
2. 倒计时运行阶段使用本机单调时钟加上最后一次可接受的 `offset`，不要在最后一秒反复请求电商站点。
3. 每个业务时间源只代表其返回该时间的网关/边缘节点，不能证明下单服务、库存服务或支付服务使用同一时钟。
4. 若用户选择的源无法达到所设精度要求，应明确报“当前路径仅能估计为 ±236 ms，未达到所需 ±100 ms”，而不是只有“校准失败”。

### 对当前项目的最小改动方向（未实施）

1. 将 `date-boundary` 的 `precisionLabel` 改为与实际语义相符的“秒级估计”，并保留具体的 `uncertaintyMs`。
2. 对每个相位源设置可解释的精度门槛；门槛由用户任务决定，不用一个全局 ±100 ms 阈值掩盖差异。阈值放宽到约 ±250 ms 仍无法覆盖本次美团官网的最优样本（约 ±343 ms）。
3. 相位策略仅消费必要响应头，避免为读取 `Date` 下载无关首页正文；这可能降低延迟，但不能保证达到 ±100 ms，仍需以实测窗口验收。
4. 北京时间增加至少一个经实际验证的备源，并把 UDP 超时、校准样本数和最终使用的源显示在界面中。
5. 为直接毫秒端点增加“字段存在、数值为 13 位 epoch ms、响应状态为成功”的运行时校验；失败才进入已标注精度的后备策略。

## 明确不采纳的做法

- 把抢购脚本的 100 ms 高频业务轮询改造成时钟校准；
- 依赖 Cookie、登录态、逆向 app 签名、私有业务接口或账户请求；
- 因为历史仓库曾使用某个端点，就把它视为当前稳定 API；
- 将 HTTP `Date` 夹逼结果标成无条件的“毫秒级时间”；
- 用一次成功响应掩盖当前 RTT、缓存、失败率和误差窗口。

## 来源与证据边界

- GitHub 仓库和固定提交是其作者代码/说明的一手来源，能证明“该项目采取了什么做法”，不能证明平台长期承诺该接口或精度。
- GitHub Issue 是社区故障证据，不等同于平台官方公告；用于说明接口可能漂移，不能单独作为可用性结论。
- 对京东历史 `serverTime` 端点的“当前不可直接采用”结论来自本机 2026-07-23 的只读响应类型检查；该结论会随平台调整而变化，应在实施前重新实测。
- 对美团和淘宝闪购的结论是“本轮未找到可证实且适合公共客户端的现行毫秒接口”，不排除平台内部或授权业务接口存在其他方案。

## 附录：用户提供的 iPhone「悬浮时钟」与华为「悬浮秒表」线索（公开资料核验）

> 核验日期：2026-07-23。以下仅使用当时可公开读取的 App Store 页面、开发者官网、开发者公开政策页、App Store 评论及 GitHub 仓库检索；**未下载、安装、登录、抓包、逆向或推断私有接口**。App Store 版本说明和页面文案会随版本更新而改变。

### 1. iPhone 应用已可唯一定位，但公开页没有列出各平台的时间源或实现

用户给出的 `id1546947240` 对应 Apple 中国区的 [「悬浮时钟-抢购秒杀助手」](https://apps.apple.com/cn/app/%E6%82%AC%E6%B5%AE%E6%97%B6%E9%92%9F-%E6%8A%A2%E8%B4%AD%E7%A7%92%E6%9D%80%E5%8A%A9%E6%89%8B/id1546947240)，开发者/Seller 为 **Hangzhou OrangeJuice Technology Co., Ltd.（杭州橘汁科技有限公司）**，Bundle ID 为 `com.hzjuzhi.FloatingClock`。这些字段也可由 Apple 的 [iTunes Lookup 结果](https://itunes.apple.com/lookup?id=1546947240&country=cn) 交叉核对。开发者官网的 [产品页](https://hzjuzhi.com/) 同样将「悬浮时钟」描述为“毫秒级悬浮计时”，并给出该 Apple 产品页链接，因而开发者对应关系可以确认。

Apple 公开页确实给出了与“时间源”有关、但粒度有限的证据：

- 产品描述称“毫秒级悬浮时钟”和“多平台时间同步：主流平台全支持”，但**没有在描述中列出**淘宝、天猫、京东、大麦、拼多多、云闪付、美团或任何其他具体平台名称；
- 页面版本历史中，`5.2.3` 的说明为“时间源优化，用户可以方便的对比设备时间/时间源时间”，`5.0.1` 的说明为“时间源更灵活：可以对不同时间源进行手动微调”；
- 公开评论中有用户提出秒抢时存在 1--2 秒差并希望调节，开发者回复“时间源可以自行选择合适的，也可手动调节”。这可证明该应用的公开 UI/产品承诺包含**可选时间源和手动调整**，但不是对误差上限、采样算法、真实服务端端点或任一平台时钟实现的技术说明。

因此，用户在手机中看到淘宝、天猫、京东、大麦、拼多多、云闪付、美团等选项，与上述公开材料并不矛盾；只是本轮公开页面没有将该列表或其请求方式导出为可核验的文档。尤其不能从“有一个来源名称”推断它是公开匿名毫秒接口，也不能据此推断其访问不需要签名、账号、授权或应用专属后端。

### 2. 开发者公开材料的实现边界

开发者的 [隐私政策](https://doc.hzjuzhi.com/floatingclock/privacy) 明示适用产品名为 iOS「悬浮时钟-抢购秒杀助手」、Android/鸿蒙「悬浮时钟FloatingClock」，提供方均为杭州橘汁科技有限公司。官网的 Android 与“鸿蒙市场”下载按钮均是 `market://details?id=com.hzjuzhi.clock` 深链接。

该深链接中的 `id` 为 `com.hzjuzhi.clock`，可以记录为**官网指向应用商店时使用的候选 Android 标识**；但它不是一个可公开审阅的华为应用市场产品详情页，也没有在上述政策页中以“包名”字段出现。因此，本报告不将它升级表述为“已由华为应用市场独立确认的包名”。公开政策、服务条款和官网都没有披露时间同步端点、NTP 列表、HTTP 请求、签名方式、误差模型或“毫秒级”精度的验收方法。

### 3. 华为应用市场中「悬浮秒表」未能唯一定位

用户补充的名称是“悬浮秒表”，而开发者官方公开材料中的 Android/鸿蒙产品名是“悬浮时钟FloatingClock”，两者并非相同的公开名称。此前的公开检索未取得一个可访问、可归属到开发者、可显示包名和版本说明的华为应用市场详情页；也没有取得能将“悬浮秒表”唯一对应到 `com.hzjuzhi.clock` 或本 iPhone 应用的可靠公开记录。

故目前只能并列保留两个候选事实，不能合并为同一应用：

| 已有公开事实 | 能确认的内容 | 不能确认的内容 |
| --- | --- | --- |
| 杭州橘汁科技官网/政策页的 Android、鸿蒙「悬浮时钟FloatingClock」 | 官方确实声称提供 Android 与鸿蒙版本；官网按钮携带 `id=com.hzjuzhi.clock`。 | 华为市场实际详情页、开发者展示名、上架状态、正式包名，以及其时间源清单。 |
| 用户口述的华为「悬浮秒表」 | 用户设备上存在一个以该名称识别的应用，并观察到更多时间源。 | 是否就是橘汁科技产品；其开发者、包名、官网、版本和任一时间源实现。 |

这不是“华为不存在该应用”的结论，而是**在禁止安装、抓包、逆向及未获得可公开核验详情页的限制下，不能负责任地唯一定位**。后续如需要消除歧义，最小新增证据应是用户提供的华为应用市场详情页公开链接，或该页中可见的开发者名、包名与版本号截图；这仍只能确认产品身份，不能单独证明时间源实现。

### 5. 对本报告原结论的范围校正

本报告前文的“未找到可证实、当前公开且无需账号/签名的毫秒接口”结论，适用于 **FloatingClock 作为独立公共客户端可安全依赖的公开技术方案**，而不应被解读为“任何商业应用都无法提供这些平台名称的时间源”。这次核验已证实，至少该 iPhone 应用公开提供“可选时间源、设备时间/时间源时间对比、手动微调”的产品功能；但其公开资料仍不足以验证它是否真正获得了每个平台的毫秒服务端时间，以及它采用了何种技术。

因此，当前项目的工程结论不变：在没有可复验的公开端点和误差证据前，不能将其他应用的 UI 选项清单复制为本项目的“毫秒级”承诺。需要修正的是措辞边界：应说“**本项目尚未找到可接入并验证的公开实现**”，而不是暗示“其他应用一定没有实现”。

## 附录：大麦时间源核验（2026-07-25）

> 目的：判断能否在 FloatingClock 中新增“大麦”作为**电商抢购参照时钟**。本节只做匿名、只读的官网首页响应头检查和公开 GitHub 源码/说明核验；未登录、未保留 Cookie、未访问演出详情或订单接口、未抓包，也未进行高频轮询。

### 结论：本版不可新增为抢购参照时钟

**截至 2026-07-25，本轮没有找到可公开访问、无需登录或签名、可复测且直接返回 epoch 毫秒字段的大麦时间端点。因此“大麦”不能在本版作为具备毫秒精度的抢购参照时钟新增。**

若产品必须保留平台名称，唯一有证据的安全降级是另列为“**大麦（HTTP Date 秒级估计）**”，并在精度不足时自动回落到北京时间/NTP；它不得显示为毫秒级、不得默认用于严格倒计时，也不得以它替换北京/NTP 的最终兜底。

### 官网实测：只有秒级 `Date`，移动站还经过缓存链路

2026-07-25 对 [大麦 PC 首页](https://www.damai.cn/) 进行一次匿名 `HEAD` 读取，响应为 `200`，包含 `Date: Sat, 25 Jul 2026 14:31:07 GMT`，同时包含 `Cache-Control: no-cache, no-store, max-age=0, must-revalidate`。该响应头没有返回 JSON、13 位 epoch 毫秒字段或其他带子秒精度的公开时间字段。

对 [大麦移动首页](https://m.damai.cn/damai/home/index.html) 的同类读取先得到 `302`，最终为 `200`；最终响应虽也有 `Date`，但同时带有 `Cache-Control: max-age=120, s-maxage=600`、`X-Cache: HIT TCP_REFRESH_HIT`、`Age: 0` 和多级 `Via`。这证明该路径处在 CDN/缓存链路中；即使以 `Date` 做相位夹逼，也只能得到秒边界区间估计，不能把缓存边缘响应当作可验证的毫秒平台时钟。

HTTP `Date` 的格式是 RFC 9110 定义的 `IMF-fixdate`，只包含到秒的 `time-of-day`；规范链接：[RFC 9110 §5.6.7](https://www.rfc-editor.org/rfc/rfc9110#section-5.6.7)、[§6.6.1](https://www.rfc-editor.org/rfc/rfc9110#section-6.6.1)。因此，`Date` 头本身不是毫秒时间戳；本项目现有的两次请求夹逼法只能在实测 RTT 足够低且缓存语义可接受时，给出带不确定度的估计，不能由头字段本身保证抢购所需精度。

### GitHub/社区核验：抢票自动化不等于公开时间源

公开仓库 [Guyungy/damaihelper（固定提交 `191a8c1`）](https://github.com/Guyungy/damaihelper/tree/191a8c1beb476963b6b72d49e1b271c2cfafae88) 是本轮能定位到的、活跃度较高的大麦相关项目之一。其 [README（固定提交）](https://github.com/Guyungy/damaihelper/blob/191a8c1beb476963b6b72d49e1b271c2cfafae88/README.md) 将项目定位为“抢票助手骨架”，说明其本地 REST API 均为 `localhost:8765/api/*`，并明确默认 `dry-run`；其公开文件树中没有独立的时间源/时钟同步模块或可复用的大麦匿名毫秒时间端点。

这只能证明该公开项目没有提供本项目可直接采用的时间源，不能证明大麦或其他闭源客户端不存在内部实现。但它也不能构成本项目接入抢票请求、Cookie、Selenium 会话、逆向签名或业务接口的理由；这些路径均不符合 FloatingClock 作为独立时钟客户端的安全边界。

### 今晚版本的处理边界

| 需求 | 可安全采用的行为 | 不可采用的行为 |
| --- | --- | --- |
| 新增“大麦”名称 | 仅以“HTTP Date 秒级估计”出现；显示实际估计误差；不满足阈值即显示“精度不足，已回落北京时间”。 | 标记“毫秒级”、显示伪造的毫秒偏移，或默认为抢购倒计时基准。 |
| 严格倒计时/抢购参考 | 使用通过质量检查的北京时间多源 NTP，或已有经验证的直接毫秒字段；以本机单调时钟运行倒计时。 | 为赶版本而使用大麦首页 `Date`、缓存响应或抢票业务接口替代高精度时钟。 |
| 大麦自动校准失败 | 明示“未发现可用毫秒时间；回落到北京时间”，并保留大麦 HTTP Date 的秒级状态（如产品需要）。 | 只显示“校准失败”，或静默继续使用过期/未知精度的偏移。 |

本节结论是“**本轮未找到可公开验证的直接毫秒端点，故不可作为本版抢购参照源新增**”，不是对大麦内部服务或第三方闭源应用能力的否定。后续只有在发现并实测通过“匿名访问、无签名、直接返回可校验 13 位 epoch 毫秒字段、无业务下单副作用”的端点后，才可以把大麦升级为直接毫秒来源候选。
