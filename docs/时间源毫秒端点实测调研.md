# 时间源毫秒端点实测调研

> 调研日期：2026-07-26 至 2026-07-27
> 结论性质：本文以本机实测数据为主要证据，社区资料仅作旁证。所有探测均为匿名只读 GET/HEAD 请求，无 Cookie、无签名、无账号态，频率与应用正常校准同量级。
> 关系说明：本文推翻[前次调研](时间源校准社区与开源做法调研.md)中“未找到美团等平台毫秒接口”的结论。差异原因见「为什么前次没有找到」。

## 结论先行

**全部 8 个时间源都可以获得平台毫秒级时间。**此前只能用 HTTP `Date` 秒边界校准的 5 个源，全部找到了匿名可访问、直接返回 13 位毫秒时间戳的公开端点，并已按下表接入（毫秒策略优先，原 `Date` 相位校准保留为自动回退）：

> 本文的“8 个时间源”指 2026-07-27 调研时的 8 个基础平台源，不含之后新增的“本机时间”和“京东秒送时间”；当前完整列表以 [README](../README.md) 为准。

| 时间源 | 毫秒端点 | 取值方式 | 策略 ID |
| --- | --- | --- | --- |
| 京东 | `HEAD https://api.m.jd.com/` | 响应头 `X-API-Request-Id` 末段 13 位（`10192119733-147598-1785082638125`），与 `Date` 头交叉校验（容差 3 s） | `jd-request-id` |
| 美团 | `GET https://cube.meituan.com/ipromotion/cube/toc/component/base/getServerCurrentTime` | JSON `{"data":1785082648292,"status":0}`，要求 `status === 0` | `meituan-server-time` |
| 美团闪购 | 同美团（共用美团时基，独立采样） | 同上 | `meituan-flash-server-time` |
| 淘宝闪购 | `GET https://waimai-guide.ele.me/h5/mtop.common.gettimestamp/1.0/` | MTop `data.t`，与淘宝现有解析完全一致 | `taobao-flash-timestamp` |
| 大麦 | `GET https://mtop.damai.cn/h5/mtop.common.gettimestamp/1.0/` | 同上 | `damai-timestamp` |

北京时间（NTP）、拼多多（`_stm`）、淘宝（`h5api.m.taobao.com` MTop）维持原状。

## 调研方法：与前次的差异

前次调研核验的对象是**各平台官网首页的响应头**与 GitHub 仓库文档；本次改用两条新路径：

1. **按基础设施推理**：大麦、饿了么与淘宝同属阿里，阿里各 BU 共用 MTop 网关架构，而 `mtop.common.getTimestamp` 是 MTop SDK 用于时钟同步与签名自举的接口，每个 BU 网关都会部署——本项目已在生产使用的 `h5api.m.taobao.com` 就是同一接口，只需替换网关域名。
2. **挖掘响应头**：许多网关会在请求 ID/追踪 ID 中嵌入毫秒时间戳。京东 `api.m.jd.com` 的 `X-API-Request-Id` 即属此类，且该域名正是原 `jd-phase` 策略在用的 URL——毫秒数据一直存在于响应中，只是此前只读取了 `Date` 头。

美团 `cube.meituan.com` 端点来自社区抢券脚本的公开记录（见文末旁证），非推理所得。

## 实测证据（三层验证）

验证脚本对每个端点采样 6–8 次，采样间隔刻意避开 1000 ms 整数倍以覆盖秒内不同相位。判据与结果：

### 1. 毫秒真实性：末三位分布

若字段是“秒 × 1000”的假毫秒，末三位恒为 `000`。实测各端点末三位均匀分布（示例：大麦 `207/543/21/624/370/252`；京东 `188/529/993/601/332/206`），排除假毫秒。

### 2. 实时性：偏移稳定度

若响应来自缓存或陈旧值，`offset = remote − 本机请求中点` 会在采样间漂移。实测热连接下每个端点的 offset 波动 ≤ 2 ms（首次采样含 TLS 握手，RTT 偏大属预期）：

| 端点 | offset 序列（ms） | 热连接波动 | 最小 RTT |
| --- | --- | ---: | ---: |
| 淘宝 h5api（对照，已在用） | 369, 308, 307, 308, 308, 307 | 1 ms | 32 ms |
| 大麦 mtop | 360, 309, 309, 309, 309, 309 | 0 ms | 45 ms |
| 饿了么 waimai-guide | 382, 310, 311, 310, 310, 310 | 1 ms | 48 ms |
| 美团 cube | 373, 313, 315, 314, 315, 314 | 2 ms | 50 ms |
| 拼多多 _stm（对照，已在用） | 351, 313, 312, 313, 313, 312 | 1 ms | 28 ms |
| 京东 X-API-Request-Id | 386, 316, 316, 316, 315, 317 | 2 ms | 42 ms |

### 3. 跨平台互证（最强证据）

六家互相独立的公司在同一时段测得的本机偏移：淘宝 307 / 大麦 309 / 饿了么 310 / 拼多多 313 / 美团 314 / 京东 316——**相互吻合在 9 ms 内**。除非它们都是真实的 NTP 驯化毫秒时钟，否则不可能出现这种一致性。这同时反向验证了本项目现有的采样与偏移计算实现。

### 附加核验

- 京东每个样本的 `X-API-Request-Id` 毫秒值与同响应 `Date` 头同秒吻合（`agreesWithDate` 全真），HEAD 与 GET 均携带该头。
- 全部端点在应用真实请求头（`User-Agent: FloatingClock/0.1` + `Cache-Control: no-cache`）下复测通过，不挑 UA。
- `src-tauri` 的 reqwest Client 为 `OnceLock` 共享实例，连接复用后第 2、3 次采样即为热连接；配合“三次采样取最小 RTT”，实际不确定度约 ±14–26 ms，远低于 `MAX_MILLISECOND_UNCERTAINTY_MS = 100` 门槛。

## 为什么前次没有找到

前次调研的检索范围是官网首页响应头 + GitHub 文档层证据，且把“未在公开仓库找到”谨慎地表述为“未找到可证实方案”。该谨慎本身正确，但检索没有覆盖：各 BU 独立的 API 网关（MTop 族）、响应头中嵌入的毫秒字段、以及以关键词（如 `getServerCurrentTime`）检索社区博客的路径。本次补上这三条后，5 个源全部有解。

## 风险与缓解

| 风险 | 等级 | 说明 | 缓解（已实施） |
| --- | --- | --- | --- |
| 端点变更或下线 | 中 | 全部是未文档化的公开接口，与已在用的拼多多 `_stm`、淘宝 MTop 同性质；京东旧接口 `a.jd.com/ajax/queryServerData.html` 的死亡（现 302 到错误页）说明此类接口确会消失 | 运行时严格校验 + 原 `Date` 相位策略保留为逐源自动回退；失败走既有“保留上次偏移/暂用本机时间”链路 |
| 京东头语义漂移 | 中高 | `X-API-Request-Id` 是请求 ID 而非时间 API，五个端点中语义最“顺带” | 解析要求末段恰为 13 位数字，且与 `Date` 头偏差 ≤ 3 s，任一不满足即弃用并回退 |
| cube 路径迁移 | 中 | `ipromotion/cube` 是美团活动组件路径 | `status === 0` 且 `data` 为有限数值才采纳；失败回退 |
| MTop 反爬（RGV587 等） | 低 | 高频请求可能触发；本应用每 10 分钟 3 次采样，量级无感 | MTop 失败响应无 `data.t`，解析自然失败并回退 |
| 美团闪购与美团共钟 | 说明性 | 闪购无独立毫秒端点，与美团共用 cube（同一美团 NTP 集群，跨平台互证支持该时基有效）；两源仍独立采样，回退 `Date` 仍用各自域名 | README 已如实披露 |

## 接入实施摘要（2026-07-27）

- [src-tauri/src/lib.rs](../src-tauri/src/lib.rs)：`strategy_request` 新增 5 个策略 ID（`cache_bust = false`，普通 3.5 s 超时）；Rust 单测同步。
- [src/time-core.js](../src/time-core.js)：新增 `parseJdRequestId(headers)`（13 位校验 + `Date` 交叉校验）与 `parseMeituanBody(body)`（`status === 0` + 有限数值校验）；大麦、饿了么复用 `parseTaobaoBody`。
- [src/time-sources.js](../src/time-sources.js)：5 个源的策略链前插毫秒策略，`precision: "millisecond"`；原相位策略与降级提示逻辑不变。
- UI 无改动：显示精度由 `precision`/`supportsMilliseconds` 字段驱动，不硬编码源 ID。
- 测试：`npm test` 22/22 通过（新增解析正反用例；美团回退链路用例改为“毫秒失败 → Date 回退”）。
